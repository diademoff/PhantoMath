# 06. План переписывания

**Цель:** Flutter-клиент + Python-бэкенд с символьным решателем.
**Вне scope:** камера/OCR, bookpoint, professor, subscription, авторизация,
анимации уровня C.

## Что точно НЕ нужно переносить

- `.rtttl` (4.6 MB, 5 моделей) — только OCR камеры
- `libpruneau.so` — Snap SDK
- Firebase, Facebook SDK, OkHttp, Glide/Picasso, Material — 8800 классов
- bookpoint / professor / subscription / authentication — 222 класса
- `NodeRuntime.js` — исполняется нативно, наш бэкенд его не зовёт

**Экономия: ~94% классов отброшено на этапе отсева.**

## Архитектура

```
┌──────────────────────────────┐
│ Flutter app                  │
│  ввод (своя клавиатура)     │
│  рендер CoreNode → LaTeX     │
│  рендер: flutter_math        │
│  список шагов + раскрытия    │
│  (микро-анимации)            │
└──────────────┬───────────────┘
               │ HTTP/JSON  ( контракт из 03-solver-contract.md)
┌──────────────▼───────────────┐
│ Python backend  FastAPI      │
│  parser  : текст → CoreNode  │
│  solver  : sympy             │
│  explain : шаги + ключи      │
│  i18n    : explanations.json │
└──────────────────────────────┘
```

## Принятые решения

| Вопрос | Решение |
|---|---|
| Бэкенд | **FastAPI**, зависимости через **uv**, локальный venv, без Docker |
| Математика | **sympy** |
| Рендер формул во Flutter | **flutter_math** (собственный рендер отклонён) |
| MVP: математический раздел | **определить по итогам исследования**, не заранее |
| APK в репозиторий | **не коммитим** (17 МБ), лежит локально в `.truth/` |
| Камера | **вне scope** |
| Анимации | вариант **B** (микро-анимации из шагов), не C |
| Структура репозитория | `backend/` + `app/` + `truth/` |
| Целевая платформа | **Android** (Flutter 3.47.7 stable, Dart 3.13.5) |
| Проверки | backend: pytest + ruff + mypy strict; app: flutter analyze + flutter test |
| Формат входа решателя | **AST-JSON, повторяющий `CoreNode`** (не LaTeX, не инфикс) |
| С чего начать | **исследование**: восстановить протокол входа Photomath |
| Редактор/клавиатура | **структурный редактор**: собственное дерево `ENode` + курсор-путь, клавиша вставляет узел/шаблон в позицию курсора |
| Рендер редактора | **дерево виджетов** (`Text` + композиции `Row`/`Column`) с мигающим курсором и тапом по элементу; `flutter_math` — для формул в шагах и ответе |
| Набор клавиш v1 | **базовый + доп. панели** (числа, функции, степени/корни, отношения, переменные, исчисление, комбинаторика) |
| Графики | **отложены** (P3): свой рендер через символьное семплирование на бэкенде, не `CoreGraphResult` |
| Выбор вставки клавиши | шаблоны-конструкции (дробь, степень, корень, модуль, скобки) **поглощают предыдущий операнд**; функции/исчисление вставляются пустыми |
| Единицы угла | узлы-обёртки **`DEGREE`/`RADIAN`** (постфиксные, 1 ребёнок), как в Photomath; аргумент без обёртки — **радианы**; обратные функции возвращают π-кратные |
| Объём тригонометрии | прямые + обратные + гиперболические + обратные гиперболические; упрощения (чётность, периодичность, тождества, формулы углов); уравнения с линейным аргументом и промежутком |
| Неточные тригонометрические значения | **остаются символьными** (`sin(1)`), как `√2` в степенях |

## Правила оформления

- **Не указывать сроки и оценки времени.** Ни в плане, ни в отчётах.
  Допустимы только приоритеты и оценки сложности.
- Архитектурные решения не принимать без вопроса пользователю.

## Этапы

### Этап 0 — формат ввода — **СДЕЛАНО**

**Блокер для всего остального.** Не восстановлена строка, которую редактор
передаёт в `nativeProcessExpression`.

Варианты:
1. Трассировка `c.a.a.a.u.a.*` (writer сериализует дерево редактора в строку).
2. Взять формат из `InternalCoreInput`/`InternalCoreNode` — это уже JSON-подобная
   структура, возможно строка = компактный JSON того же дерева.
3. **Рекомендация:** не восстанавливать, а **задать свой формат входа**
   (LaTeX-подобный или наш AST-JSON) и сразу проектировать под него. Формат
   входа — внутренняя деталь Photomath, совместимость с ней нам не нужна.

Результат: TypeScript-описание `Node` во Flutter + парсер в Python,
покрывающий те же 143 `CoreNodeType`.

### Этап 1 — типы и рендер ядра — **ЧАСТИЧНО**

- Перенести `CoreNodeType` (143) как `enum` в Python и Dart.
- Написать сериализатор/десериализатор в формате `03`.
- Flutter-рендер `CoreNode` → `TextSpan`/`Widget`:
  дробь, корень, степени, матрицы, модули, скобки, пределы, интегралы.
  **Это ~40% объёма фронтенда.** Ориентир — `editor/preview/view/EditorView`.

Проверяемо: вывод выражения совпадает с оригиналом на наборе тестов.

### Этап 2 — объяснения — **СДЕЛАНО**

- Загрузить `truth/data/explanations.json`.
- Резолвер `CoreRichText(type, args)` → текст: подстановка `ARGn`,
  обработка `[label|uuid]`, fallback на `default` при отсутствии локали.
- Тест: все 3252 ключа резолвятся без `?? step_xxx ??`.

### Этап 3 — символьный решатель (основа) — **В РАБОТЕ**

Сделаны модули (`backend/mymath_backend/solver/`, по файлу на модуль):

| Модуль | Что делает |
|---|---|
| `arithmetic.py` | порядок действий, `+ − × ÷ ^`, скобки, неявное умножение |
| `fractions.py` | сокращение дробей, смешанные числа |
| `powers.py` | точные корни и логарифмы (`√16`, `log₁₀(1000)`, `ln e`) |
| `trigonometry.py` | прямые, обратные и гиперболические функции; единицы угла `DEGREE`/`RADIAN`; чётность/нечётность и приведение к наименьшему котерминальному углу |
| `equations.py` | линейные и квадратные уравнения (дискриминант, корни через `√`) |
| `inequalities.py` | линейные неравенства (со сменой знака) |
| `systems.py` | системы 2×2 линейных уравнений (Крамер) |
| `matrices.py` | определители 2×2…5×5 |
| `derivatives.py` | производная: свои правила для многочленов, sympy-фолбэк для остального (`sec`, `x^x`, …) |
| `limits.py` | предел через sympy: конечная точка, бесконечность, односторонний, раскрытие неопределённостей |
| `integrals.py` | неопределённый и определённый интеграл (sympy) |
| `series.py` | суммы (знак суммирования) |
| `combinatorics.py` | факториал, `C(n,k)`, перестановки, размещения |
| `complex.py` | `Re`, `Im`, сопряжение; арифметика с `i` через sympy |
| `vectors.py` | векторы (узел `LIST`) и операции командами: длина, сумма, разность, скаляр, скалярное и векторное произведение |
| `commands.py` | действия `CoreAction`: `factor`, `expand`, `simplify`, векторные; `expand` раскрывает формулы углов (`trig=True`); тождества сворачивает запасной проход `simplify` |
| `sympy_bridge.py` | не модуль, а слой: `CoreNode ↔ sympy`, `simplify_node` |

**Символьный слой появился.** Мост `sympy_bridge.py` переводит дерево в
sympy и обратно, поэтому результат-выражение возможен: интегралы, суммы и
разложение/раскрытие возвращают выражение, а не число.

**Слой команд.** `POST /solve` принимает необязательное `action`
(`CoreAction`), как в Photomath. Команды `factor`/`expand`/`simplify` покрывают
операции без своего типа узла. Имена команд — наши (в APK восстановлен только
пример `solve`); для уравнения команда применяется к обеим частям.

**Векторы** сделаны своим представлением (в контракте типа вектора нет):
вектор — узел `LIST`, операции — команды. Выбор способа решения сделан для
квадратных уравнений и ссылок.

«Нет решений» и «бесконечно много решений» теперь **нормальный ответ**: шаг с
ключом ``false_statement_solve`` или ``solutions_inf_many`` и без узла ответа
(``solution = null``) — текст шага и есть ответ (см. `09-decisions.md`).

**Выбор способа решения.** Квадратное уравнение отдаёт два способа (формула и
разложение, если корни рациональны): это отдельные записи вертикальной ветки,
`selectMethodText` — подпись переключателя. Клиент показывает первый способ и
даёт переключиться. Линейные уравнения пока решаются одним способом; механизм
общий. Ссылки `[label|uuid]` внутри текста шагов распознаются резолвером
(попадают в `explanation.links` как `{label, uuid, definition}`) и нажимаемы
в приложении. Определения понятий — **наш глоссарий** (`concepts.py`,
9 понятий для текущих модулей, ru/en), содержимого из APK нет. Тап по ссылке
открывает карточку с определением; если определения нет — переключает способ
(когда их несколько). У части русских шаблонов ссылок нет вовсе (свойство
данных) — тогда определения не будет.

Технологии: **sympy** для символьных операций, **sympy.parsing.latex**
(antlr) для парсинга, свой слой правил для пошаговых объяснений.

| Модуль | Покрытие | Сложность |
|---|---|---|
| Арифметика: порядок действий, скобки | 100% | низкая |
| Рациональные числа, дроби, НОД/НОК | 100% | низкая |
| Уравнения: линейные, квадратные, радикалы | 100% | низкая |
| Системы уравнений | 100% | средняя |
| Степени, логарифмы, показательные | 95% | средняя |
| Тригонометрия (таблицы, аргументы, формулы) | 90% | высокая |
| Многочлены: разложение, деление, делители | 90% | высокая |
| Неравенства | 85% | высокая |
| Последовательности и ряды | 70% | высокая |
| Пределы, производные | 85% | средняя |
| Интегралы | 70% | высокая |
| Векторы, матрицы, определители | 60% | высокая |
| Комплексные числа | 50% | средняя |

Метод работы: для каждого модуля — **сначала ключи объяснений**, потом
алгоритм. Ключи из `explanations.json` — это готовый чек-лист шагов:
если модуль «Системы уравнений» ссылается на 40 ключей, значит известно,
какие именно подшаги он обязан порождать.

### Этап 4 — вертикальные шаги — **В РАБОТЕ**

Формат вывода — `CoreSolverVerticalResult` (см. `03.5`), он простой:
`steps[] { stepHeaders[], substeps[] { description, left, right, subresult[] } }`.

Сделано для арифметики и линейных/квадратных уравнений: шаги с ключами из
словаря, заголовок шага «Решите уравнение», тексты подставляются на бэкенде.

Ключевая сложность — **выбор пути решения**. Photomath перебирает методы
(квадратный формулой? факторизацией? вынесением общего множителя?) и
предлагает переключение — это те самые `[label|uuid]`.
Наша версия: фиксированная очередность методов + переключатель для
основных случаев.

Не оценка сроков, а степень понимания предмета по результатам разбора APK.

| Этап | Что понятно | Что неизвестно |
|---|---|---|

## Риски

| Риск | Вероятность | Влияние | Митигация |
|---|---|---|---|
| Объём объяснений больше ожидаемого | высокая | критическое | Сократить до вертикально-основного (арифметика, уравнения, степени, логарифмы) ≈ 20% ключей |
| Не найден алгоритм выбора метода решения | средняя | высокое | Использовать эвристики, не паритет |
| Рендер формул в Flutter дорог | высокая | среднее | Взять готовый движок рендера LaTeX (`flutter_math`) и адаптировать |
| Права на `explanations.json` | средняя | высокое | Заменить своим текстом, оставив ключи и арность |
| Timezone/локаль vs decimal separator | низкая | среднее | Уже есть в `enums` (`CONSTANT_PERIOD`, `UserProfileDecimalSeparatorActivity`) |

## Первое действие

Не начинать с решателя. Начать с **тестового корпуса**: собрать 100-200
задач, для которых известен эталонный вывод Photomath, и добиться
воспроизведения вертикальных шагов. Это даст метрику прогресса и
одновременно покажет реальную сложность каждого модуля.

Корпус можно генерировать: ключи в `explanations.json` задают структуру
шагов, от обратного можно восстановить типичные задачи по модулям.
